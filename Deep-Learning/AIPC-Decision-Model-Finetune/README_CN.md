## 目的

**专用决策模型（decision model）正在成为一类独立的模型**：TypeSafe 的托管模型 Jev、2026 年 9 月开源的 [Kev](https://github.com/jaredpalmer/kev)（10 月 1 日发布 1.0），以及 llama.cpp 当前版本已能服务的十来个同类模型。它们不生成文字，只在给定选项里选答案并给出概率：一次前向就完成路由、分诊、判级这类业务判断，比让聊天模型写一段再解析更快、更稳、更便宜。但如果这类模型只能放在云上，对边缘设备、离线场景和数据不出本地的客户并不友好。所以它要满足两点：

1. **能在本地运行**——笔记本的 CPU 和内存就要跑得动，不调用云端模型。
2. **能接入业务数据微调**——客户的规则、字段和术语要能训进模型，规则变了还能更新。

本项目用 Kev（基于 Qwen3.5 的开放权重决策模型，0.8B / 4B）验证这两点：在 GPU 主机上用业务数据微调，在骁龙笔记本上测准确率、时延和内存，逐项测量量化、上下文长度、计算后端、提示词长度和模型规模这些推理优化杠杆的效果，再把同一个模型文件放到一台 x86-64 虚拟机上确认照常运行。**训练在 GPU 主机完成，日常推理留在笔记本，不调用云端模型。** 数据是 Contoso PC 模拟数据，不是真实客户数据；不含云端闭源模型对比，不作生产可用性承诺。

## 架构

配方名称：**B0** 是不训练的 Kev 发布版；**B0-policy** 是同一个发布版，但把厂商规则全文写进每个问题的提示词；**FT** 是用业务数据在发布版上做监督微调；**FT-cf** 是 FT 的数据再加"只改一个设备字段"的反事实变体；**第二轮 C** 是 FT-cf 的配方再加 206 条针对薄弱字段的变体、训 4 个 epoch。FT、FT-cf 和第二轮 A/B/C 都从同一个发布版出发、各自独立训练；**最终推荐和交付的是第二轮 C**（`Contoso-Kev-0.8B-FTcf-R2C-Q8_0.gguf`），FT-cf 是它的上一版，第 1–7 节保留第一轮各配方的测量；C 的 GPU 数字见[第二轮](文档/评测与端侧结果全集.md#round2)，在 x86-64 虚拟机和骁龙笔记本上的端侧数字见[端侧回归](文档/评测与端侧结果全集.md#round2-device)。

#### 模型组成：本次微调改哪些部件

本段指本项目使用的 **`jaredpalmer/kev-0.8b@v1.0` LoRA 检查点**，不泛指所有 Kev 版本或格式。它保存已训练的 adapter、决策头、配置和分词器文件，**不是独立的全量基座权重包**，需要配合指定版本的 Qwen 基座加载。

**运行中的 Kev-0.8B = Qwen3.5-0.8B 基座 + Kev 已训练的 LoRA adapter + 已训练的决策头。** `0.8B` 是基座的规模档位，不是 adapter 也有 0.8B；`v1.0` 是发布版本，不是第二个模型。

- **Qwen 基座：冻结，不更新。** `--base` 和 `--base_revision` 指定主干权重及其版本。
- **Kev LoRA adapter：继续训练，更新参数。** `--init_from` 加载 v1.0 已有的 LoRA；本次在这同一套参数上继续学习业务数据，**不叠加第二套业务 adapter**。
- **Kev 决策头：继续训练，更新参数。** 它也由 `--init_from` 加载，用于给输入中的候选选项打分；不是重新随机初始化一个头。

**微调阶段更新的是后两项。** 随后的校准阶段冻结权重，只拟合温度 T。导出 GGUF 时，将更新后的 LoRA 合并进基座，并打包决策头、分词器与温度；客户拿到的最终 GGUF 已包含独立加载所需内容，**不需要再单独加载 Qwen 基座或 adapter**，但仍需 llama.cpp 运行时。

依据：[本次 C 训练配置](验证结果/第二轮微调评测_20261101-101948/runs/0.8b/r2-C/training_config.json)中的 `lora=16`、`full_ft=0`、`init_source`，以及 [Kev `Checkpoint.warm_start()`](https://github.com/jaredpalmer/kev/blob/2074cc44256200bb37540103fa4572901faa10f3/kev/checkpoint.py) 的已有 adapter 与决策头加载逻辑。

#### 核心代码示例：微调、校准、量化

以下按当前交付的 **0.8B C 配方**展开核心调用。先完成[训练环境、数据上传与导出工具准备](文档/操作步骤全本.md#train-update)，在 Linux 训练主机的同一个 Bash 会话中顺序执行；前两步需要 GPU，导出与量化只用 CPU。示例使用本项目的实际路径，**不要在已有检查点或结果目录上重复执行**。完整复现仍使用链接中的流水线，它还包含评测、错误处理和交付校验。

**1. 微调：业务样本 → LoRA 与指针头检查点。** C 使用 4,038 条业务记录、1,000 条通用回放，训练 4 个 epoch；基座权重冻结。[完整训练脚本](scripts/remote_round2.sh)

```bash
set -euo pipefail
cd /mnt/aipc/kev
PY="$PWD/.venv/bin/python"
CK=/mnt/aipc/runs/0.8b/r2-C
"$PY" -m kev.train \
    --data /mnt/aipc/data/contoso/train_cf2.jsonl --suite evals/v7/decision-v7 --replay 1000 \
    --base Qwen/Qwen3.5-0.8B-Base --base_revision dc7cdfe2ee4154fa7e30f5b51ca41bfa40174e68 \
    --init_from jaredpalmer/kev-0.8b@v1.0 --epochs 4 --lr 2e-5 --batch 4 --accum 2 \
    --dtype bf16 --checkpointing 1 --max_state 768 --device cuda --seed 1 --out "$CK"
```

**2. 校准：校准集分数 → 检查点中的温度 T。** 先保存固定模型的逐题分数，再拟合温度；不更新模型权重，不改变答案排序，也不使用测试集挑温度。[校准与更新说明](文档/操作步骤全本.md#calibration-update)

```bash
ROWS=/mnt/aipc/runs/0.8b/r2-C-calib-raw
"$PY" -m kev.benchmark --run "$CK" \
    --data /mnt/aipc/data/contoso/calib.jsonl --out "$ROWS" --device cuda
"$PY" scripts/calibrate_checkpoint.py --run "$CK" \
    --rows "$ROWS/rows.json" --allow-in-distribution
```

**3. 导出并量化：已校准检查点 → BF16 GGUF → Q8_0 GGUF。** 转换器合并 LoRA 并写入指针头与温度；量化不重训。生成的 Q8_0 文件仍需温度核对和目标设备回归，不能仅凭导出成功认定效果不变。[完整导出脚本](scripts/remote_export_round2.sh)

```bash
LLAMA=/mnt/aipc/llama.cpp
OUT=/mnt/aipc/gguf/0.8b-r2C
NAME=Contoso-Kev-0.8B-FTcf-R2C
mkdir -p "$OUT"
/mnt/aipc/llama-venv/bin/python "$LLAMA/convert_hf_to_gguf.py" "$CK" \
    --outtype bf16 --outfile "$OUT/$NAME-BF16.gguf.part" --model-name "$NAME"
mv "$OUT/$NAME-BF16.gguf.part" "$OUT/$NAME-BF16.gguf"
"$LLAMA/build/bin/llama-quantize" "$OUT/$NAME-BF16.gguf" "$OUT/$NAME-Q8_0.gguf.part" Q8_0
mv "$OUT/$NAME-Q8_0.gguf.part" "$OUT/$NAME-Q8_0.gguf"
```

## 实现效果

### 输入什么，输出什么

仓库保留三个真实单题调用例子，使用 0.8B C / Q8_0，在 x64 上运行；**不是骁龙基准，也不是中位耗时**：

- 订单进度询问，输出 `sales_ops`，与规则标签一致。
- “帮我联系人工客服咨询保修。”，输出 `support_chat`，与规则标签一致。
- 德国设备有意外损坏保修、键盘进液，模型输出 `sales_ops`，正确标签是 `damage_claim`，该题答错。

[查看每个例子的完整输入、完整输出、对错与当次处理时间](文档/评测与端侧结果全集.md#request-examples)。模型只做分类，不实际执行维修或联系操作。

### 长上下文测到什么

**测过长输入，没有测出绝对最大上下文。** 在 x64 的 0.8B C、`-c 8192` 配置下，160 条长历史模拟工单有 7 条未返回答案；其余 153 条共 459 道判断答对 206 道，准确率 44.9%，完整请求中位耗时 26.395 秒。最长成功请求的输入总量为 24,155 token（三道题合计，均摊约 8,052），不是精确测出的单题上限。没有逐档扩大窗口，也没有完成骁龙或 4B 的最大长度测试。[原始记录、拒绝原因与边界](文档/评测与端侧结果全集.md#long-input)。

### 各项结果与证据

- **微调与泛化：** 主矩阵在上方；完整的发布版、提示词对照、FT、FT-cf、第二轮 A/B/C 及剩余错误见[评测全集](文档/评测与端侧结果全集.md#same-questions)。
- **通用能力：** 656 道公开题用于检查遗忘；概率质量单列，不用准确率代替。[通用题结果](文档/评测与端侧结果全集.md#2-通用能力有没有丢)
- **校准：** 调温度只改概率，不改答案排序；概率偏差与需要重训的错误分别处理。[校准边界](文档/评测与端侧结果全集.md#3-校准答案排名正确概率仍可能不准)
- **训练资源：** 第二轮 C 训练耗时 22 分 42 秒，整卡显存峰值 7,475 MiB；没有重测多个随机种子。[训练成本](文档/评测与端侧结果全集.md#4-训练要多少资源)
- **跨架构：** 同一 C 文件在骁龙和 x86-64 上有 982/987 题答案相同，不是完全相同；不比较两台机器谁更快。[端侧回归](文档/评测与端侧结果全集.md#round2-device)
- **并发与长输入：** 骁龙的五档并发未显示吞吐随并发增长；长历史准确率不足是另一项限制。[并发](文档/评测与端侧结果全集.md#concurrency-laptop) · [长输入](文档/评测与端侧结果全集.md#long-real)
- **本机试用与第二轮：** 保留早期错误、后续修正和不成立的预判，不把成功响应当正确答案。[本机试用](文档/评测与端侧结果全集.md#local-result) · [第二轮完整对照](文档/评测与端侧结果全集.md#round2)

### 推理优化：测过哪些杠杆

量化、上下文长度、计算后端、提示词长度、模型规模、长输入、并发与 CPU 架构的原有完整矩阵保留在[方法与每次运行](文档/评测与端侧结果全集.md#推理优化测过哪些杠杆)。这些时延按完整请求统计，不当作独立单题耗时。


### 硬件要求

训练显存、笔记本内存和模型文件大小见[实测硬件表](文档/评测与端侧结果全集.md#6-需要什么硬件)。表中是指定负载的实际占用，不是所有设备的最低可用配置。


### 结论边界

模拟数据、单个训练 seed、一台骁龙笔记本和一台 x86-64 虚拟机；没有客户生产验收、长期稳定性或电池功耗结论。测试集错误已用于配方迭代，因此现有分数不是独立盲测终验。分布外结果仍是模拟业务，长输入不能采用短输入准确率承诺。[完整边界](文档/评测与端侧结果全集.md#这些结论的边界)

### 已有模型：启动并发一条请求

第一个 PowerShell 终端启动服务；第二个终端发送请求。看到每道题的候选概率才算调用成立，正确性仍须与业务规则核对。

```powershell
$Engine = 'C:\Tools\llama.cpp\b11935-cpu\llama-server.exe'
$Model = 'C:\Tools\models\contoso-kev\Contoso-Kev-0.8B-FTcf-R2C-Q8_0.gguf'   # 交付的第二轮 C；上一版改用 Contoso-Kev-0.8B-FTcf-Q8_0.gguf
if (-not (Test-Path -LiteralPath $Engine)) { throw '找不到 llama-server' }
if (-not (Test-Path -LiteralPath $Model)) { throw '找不到微调 GGUF，请先取得模型' }
& $Engine -m $Model --alias contoso-kev-0.8b-r2c --host 127.0.0.1 --port 8080 `
    -c 8192 -b 2048 -ub 2048 -ngl 0 --cache-ram 0 --offline
```

Invoke-RestMethod -Uri http://127.0.0.1:8080/health
