## 结论先说

阶段性报告（2026-10-27）：训练、PyTorch 评测和端侧测试已完成；4B 在笔记本上只完整测了推荐的 FT-cf。

- **微调：在本次模拟数据上有提升。** 基础业务训练集为 2,147 条，FT-cf 加入反事实变体后为 3,832 条，均另混入 1,000 条 Kev 原训练数据。推荐配方 FT-cf 的同分布测试集准确率，0.8B 从 44.7% / 67.1%（工单 / 助手）提到 86.9% / 97.5%，4B 从 60.8% / 81.8% 提到 95.9% / 99.8%。另一个模型写原话的分布外测试集上，0.8B 是 82.5% / 94.4%，4B 是 91.4% / 98.8%。两个配方各自从发布版训练，不是从 FT 连续训练成 FT-cf。
- **性能：总体准确率提升，业务阈值还需独立验收。** B0-policy 比 FT 低 10.5–30.2 个百分点。按测试集标签计算的 5% 错误预算覆盖率，FT-cf 同分布结果为 0.8B 84.5% / 100%、4B 100% / 100%，发布版为 2.9%–43.2%；这不是固定阈值上线后的错误率保证。Kev 公开题上准确率变化在 −0.8 到 +0.9 个百分点之间，未触发下降超过 2 个百分点的遗忘判定线，但 Brier 变差了。
- **资源：一张 H100 NVL 上一次训练 12–27 分钟，按列表价 1.8–4.1 美元。** 用 micro-batch 1 时显存峰值 0.8B 4,213 MiB、4B 18,547 MiB（nvidia-smi，在最长的训练记录上实测）。笔记本上 Q8_0 文件 0.8B 775 MiB、4B 4,276 MiB，进程峰值工作集 0.8B 2,314 MiB、4B FT-cf 9,609 MiB。
- **推理引擎：llama.cpp 能直接跑微调后的模型。** 0.8B FT 和 FT-cf 的 Q8_0 在骁龙 X Elite CPU 上与 PyTorch 逐题一致率 99.2% 以上，单次决策时延中位数 0.65–0.98 秒；4B FT-cf 的 Q8_0 一致率 99.4% / 100%（工单 / 助手），3.6–4.1 秒。Adreno GPU 版更慢、偏差更大；Q4_K_M 省内存，但没有测出更快，偏差更大。
- **还没解决：** "能否上门"要同时看问题类型、保修类型、购买天数和地区，0.8B 在这道题上的平衡准确率只有约 55%，4B 在分布外测试集上是 66.7%，低于 B0-policy 的 88.1%；0.8B 在购买天数、地区、电池循环次数上，答案因字段改变的题只答对 36–49%。所有结论来自模拟数据和一次训练（seed 1）。

## 1. 本报告验证什么

业务目标是一个能在笔记本本地运行、判断准确、响应快、资源占用低，并能由客户用业务数据更新的决策模型。云端服务不能直接部署到端侧，通用模型也不等于已经适配客户业务；本项目以 Kev 为候选验证这条路径，未做云端闭源模型的对照评测。

工单分诊和助手路由是验证场景，分别每条 3 道问题。本报告依次检查：业务微调效果与规则跟随、校准与通用能力回归、训练资源、端侧运行与引擎一致性。连续业务更新和自动发布未在本轮实测，不能由两个独立训练配方推断它们已经实现。

## 2. 做法

| 环节 | 做法 | 关键设定 | 代码 |
|---|---|---|---|

| 切分 | 按原话分组哈希切分，配对样本跟着原话走，不跨切分 | 训练 70% / 校准 10% / 开发 10% / 测试 10%；分布外数据只做测试 | 同上 |
| 微调 | 监督微调（SFT），损失是每道题正确选项上的交叉熵，不是强化学习（Kev README："Training uses cross-entropy on the correct answer"；[本次训练配置](../验证结果/微调评测_20261027-220226/runs/0.8b/ft/training_config.json)里 `perm_kl`、`ord_w`、`label_smoothing`、`brier_w`、`focal_gamma`、`anchor_w` 都是 0）。续训方式按 Kev 官方 README：`--init_from` 从发布版检查点加载 LoRA 和 pointer head 继续训练，再混入 1,000 条 Kev 原训练集防止遗忘，最后在校准集上拟合温度 | LoRA r16、2 epoch、lr 2e-5、有效 batch 8、bf16、seed 1 | [scripts/remote_pipeline.sh](../scripts/remote_pipeline.sh)、[scripts/remote_pipeline_v2.sh](../scripts/remote_pipeline_v2.sh) |

- **公开版数据**：仓库里的数据把记录中生成模型的名字换成了代号 `llm-A`（大模型 A）和 `llm-B`（大模型 B），其余内容与实验所用数据相同，所以 `manifest.json` 的 SHA-256 与实验时不同。
- **标签复核**：用厂商策略代码按每条记录自己的设备字段重算标签，8 个文件 3,802 条记录全部一致，见 [验证结果/数据标签复核_20261027-130518.txt](../验证结果/数据标签复核_20261027-130518.txt)。
- **多数标签基线**：总是回答最常见的标签，工单测试集能对 54.5%（"能否上门"一题有 89% 是"否"），助手测试集能对 58.3%。所以下面除了准确率，还给每个问题的平衡准确率（各标签召回率的平均）。
- **原话重复**：助手场景的短指令会重复，助手测试集有 19 条记录的原话和训练集某条原话完全相同（设备状态不同）。结果里另给去掉这 19 条后的对比。工单测试集和两个分布外测试集没有这种重复。
- **分布外缺口**：助手分布外的 300 条用例中，13 条"应拒绝"类请求（绕过安全、操作他人账号）生成模型拒绝写原话，两轮重试仍失败，所以分布外助手测试缺这一类。

**两个尺寸都调好了。** 首轮微调（FT）后，同分布测试集的准确率：0.8B 工单 44.7% → 86.5%、助手 67.1% → 93.5%；4B 工单 60.8% → 93.5%、助手 81.8% → 99.0%。每一项 FT−B0 的 95% 区间下界都远大于 0，按实验协议判定为有提升（协议指定的 `kev.compare` 宏平均口径同样成立，见上方第二张表）。第二种配方 FT-cf 又比 FT 高 0.4–4.0 个百分点，其中 0.8B 工单两个测试集的 95% 区间包含 0；按事先定的选择规则，两个尺寸都推荐 FT-cf（见 3.3）。

- **比"把规则写进提示词"好得多。** B0-policy 把 0.8B 工单只提到 60.8%、助手 71.9%，4B 工单 63.3%、助手 87.8%；FT 在同分布测试集上还要再高 11–30 个百分点（4B 助手 +11.1，0.8B 工单 +25.7，4B 工单 +30.2）。提示词的效果也不稳：0.8B 在助手分布外测试集上，B0-policy 只有 63.6%，比什么都不加的 B0（65.7%）还低。B0-policy 每条记录还要多读策略文本（工单场景平均多约 3,700 个字符，助手场景多约 1,800 个字符），端侧耗时随之变长（第 5 节）。
- **换一个生成模型、换一种数据分布，提升依然在。** 分布外测试集由另一家厂商的模型（大模型 B）写原话，新加坡、离线和按流量计费网络更多，还混入"一条消息说两件事"。FT 在分布外的准确率：0.8B 工单 81.6%、助手 91.9%，4B 工单 88.8%、助手 96.6%，比同分布低 1.6–4.9 个百分点；FT-cf 是 0.8B 82.5% / 94.4%、4B 91.4% / 98.8%，比同分布低 1.0–4.5 个百分点。这是正常的分布偏移损失；相对 B0 的提升幅度见表。
- **不是靠记住训练原话。** 助手测试集有 19 条记录的原话在训练集出现过（只是设备状态不同）。去掉这 19 条，0.8B 的 FT−B0 仍是 +27.6 个百分点（95% 区间 +23.8 ~ +31.4）。

**首轮微调的短板：设备字段用得不好。** 测试集里有一种"配对样本"：同一句客户原话，只改一个设备字段（例如保修类型、购买天数、网络），按厂商策略答案就该变。如果模型真的在用这个字段，两条都应该答对。首轮 FT 的 0.8B 在这些配对上两条都答对的比例只有 9.7%（工单）和 13.6%（助手），B0 和 B0-policy 都是 0%。0.8B 工单分派题剩下的 53 个错误里，绝大多数发生在"上门维修 / 寄修 / 付费报价 / 意外损坏理赔 / 电池计划"之间，这几个队列恰好取决于保修、地区、购买天数、电池循环这些字段。也就是说，首轮微调主要学会了"从原话判断是什么问题"，还没学会"按设备档案套用公司规则"。

**补救做法（FT-cf）。** 训练集里的每条原话额外生成最多 3 个"反事实"变体：原话不动，只改一个策略字段，标签由策略代码重算（产品线不改，因为客户原话里会写机型）。新增 1,685 条，训练集从 2,147 条变成 3,832 条，其余设置不变。为了公平衡量，评测另用开发集、测试集和分布外的原话各生成变体集（不含任何训练原话），并且只统计"答案和原话那条不同"的题：这些题只有看懂了字段才能答对。选择规则在结果出来前写进了实验协议：FT-cf 在开发集变体上比 FT 准、且开发集原题准确率下降不超过 1 个百分点，才推荐 FT-cf。

**结果：两个尺寸都满足选择规则，推荐 FT-cf。** 开发集变体（全部题）上，0.8B 从 FT 的 78.9% / 82.9%（工单 / 助手）提到 82.2% / 92.8%，4B 从 89.1% / 96.4% 提到 95.9% / 100.0%；开发集原题都没有下降（0.8B 87.7% / 94.1% → 88.4% / 97.5%，4B 93.9% / 98.4% → 95.2% / 99.6%）。

- **助手场景补得最好。** 只看答案因字段改变的题，0.8B 助手从 48.6% 到 81.9%（测试变体）、从 46.3% 到 81.7%（分布外变体），4B 助手到了 100.0% 和 98.3%。网络、是否企业管理、电源与电量这三个字段，0.8B 从 17.9–57.1% 提到 75.0–84.0%。
- **工单场景还有缺口。** 0.8B 工单只从 48.3% 到 57.6%（测试变体），差值的 95% 区间包含 0；按字段看，购买天数 41.9%、地区 36.2%、电池循环次数 49.2%，仍不到一半。这几个字段在规则里都要和阈值或名单比较（保修期天数、电池计划的循环次数 < 500 且购买不超过 730 天、上门服务的地区名单）。4B 好得多（工单测试变体 72.1% → 84.9%），但地区也只有 56.9%，低于 B0-policy 的 67.2%（这一项只有 58 题）。
- **原测试集配对题的方向相同。** 两条都答对的比例，0.8B 助手从 13.6% 到 63.6%，4B 助手从 90.9% 到 100%；0.8B 工单仍是 9.7%。这组题在设计 FT-cf 时已经看过，只作参考。
- **代价不大。** 主测试集上 FT-cf 比 FT 高 0.4–4.0 个百分点，通用题准确率 0.8B 不变、4B 升 0.9 个百分点（3.5）。

两个指标：

- **ECE（期望校准误差）**：模型说"80% 有把握"的那些题，是否真的有 80% 答对；把所有置信度区间的偏差按题数加权平均，越接近 0 越好。
- **5% 错误预算下可自动处理的比例**：把测试题按模型的置信度从高到低排列，再用该测试集的标签计算错误率不超过 5% 的最大覆盖范围。它描述本次测试上的风险与覆盖率，不是已经选定并独立验证过的业务阈值。

**微调后的概率有助于评估分流，但不能据此承诺上线错误率。** 所有 FT 测试集的 ECE 都在 0.05 以内（同分布 0.011–0.023，分布外 0.005–0.050）；FT-cf 除 0.8B 工单分布外（0.064）以外都在 0.03 以内。B0-policy 的助手场景 ECE 为 0.8B 0.175、4B 0.213。ECE 是分箱平均偏差，不能保证某个阈值以上、某个少数类别或新分布上的错误率；业务阈值需要在独立数据上选择，固定后再验证。

**本次测试中的覆盖率**：FT 同分布为 0.8B 工单 84.7%、助手 97.1%，4B 工单 96.7%、助手 100%；分布外为 0.8B 65.4% / 92.6%、4B 84.1% / 100%。FT-cf 同分布为 0.8B 84.5% / 100%、4B 100% / 100%，分布外为 0.8B 69.9% / 98.8%、4B 91.2% / 100%。B0 在同一口径下为 2.9%–44.4%。这些数字保留原评测定义，不升级为“可以放心自动处理”的部署保证。

- **两个尺寸都在一张 GPU 上完成训练。** 0.8B FT 用 micro-batch 1，耗时 26.9 分钟；4B FT 用 micro-batch 4，耗时 15.7 分钟。0.8B FT-cf 的训练记录增加 54%，micro-batch 同时改为 4，耗时 11.6 分钟；这些条件同时变化，不能把时长差只归因于 micro-batch。同样训练 9,664 条记录、micro-batch 为 4 时，4B FT-cf 用时 20.1 分钟。四次有效 batch 都是 8；FT 的 6,294 条训练记录为（2,147 + 1,000）× 2 个 epoch，FT-cf 的 9,664 条为（3,832 + 1,000）× 2。`training_metrics.json` 中四次的 `truncated_records` 均为 0。
- **显存要分清两个数。** nvidia-smi 此处是整卡显存采样，可能包含框架缓存和其他进程，并非仅训练进程的张量；PyTorch 分配峰值不包括全部运行开销。选卡需要结合实际运行条件留余量，不能把任一单次采样当作通用最低配置。
- **同一个模型，nvidia-smi 的数可以差很多。** 4B 两次训练的 PyTorch 分配峰值几乎相同（22,581 / 22,641 MiB），nvidia-smi 却相差 7,144 MiB（33,359 / 26,215 MiB），差别应来自 PyTorch 预留的缓存（推测；nvidia-smi 只记录整卡用量）。
- **显存不够时用 micro-batch 1。** 同一配方（bf16、梯度检查点、`max_state 768`）改成 micro-batch 1 × accum 8，在原话加设备档案最长的 64 条厂商训练记录上训 8 步（GPU 上没有其他进程）：nvidia-smi 峰值 0.8B 4,213 MiB、4B 18,547 MiB，PyTorch 分配峰值 3,365 / 17,375 MiB（[状态、日志和显存曲线](../验证结果/微调评测_20261027-220226/runs/memory-probe)）。这次探测没有混入 Kev 原训练集记录：0.8B 正式训练同样用 micro-batch 1，PyTorch 峰值 3,460 MiB，比探测高约 3%，所以按探测值选卡要留余量。
- **按列表价算钱。** 这台 VM 的按量价是每小时 9.07 美元（Azure Retail Prices API，Spain Central，2026-10-27；订阅的实际折扣价没有核对）。只算训练本身，0.8B 一次约 1.8–4.1 美元，4B 一次约 2.4–3.0 美元；整轮实验（环境、基线、两个尺寸、两种配方、评测、转换、显存探测）共用 VM 2 小时 53 分钟，按列表价约 26.2 美元。

怎么读这张表：

- **一致率**：同一道题，笔记本上的答案和 PyTorch 的答案相同的比例。**概率差**：两边给出的概率分布相差多少（总变差距离，0 表示完全相同，1 表示完全不同），取全部题目的平均。
- **单次决策时延**：从客户端发出请求到收到三道题全部答案的时间（一条记录 = 一次决策），p50 是中位数，p90 表示 90% 的请求不超过这个时间。前 2 条请求作为预热，不计入。
- **峰值工作集**：进程实际占用的物理内存峰值；**提交内存**：进程向系统申请的内存（含预留但未使用的部分），决定会不会挤占其他程序。4B FT-cf Q8_0 的峰值工作集（9,609 MiB）比提交内存（8,884 MiB）大，推测是因为 llama.cpp 默认把模型文件映射进内存（mmap），读进来的模型文件页计入工作集、不计入提交内存（未核实）。

**发现 1：llama.cpp 跑的就是微调后的模型，结果与 PyTorch 一致。** 转换器把 LoRA 合并进基座、把校准温度写进 GGUF 元数据（0.8B 写入 1.2599，4B 写入 1.6625，与 `head.pt` 中的值相同）。微调后 0.8B 的 Q8_0 在笔记本 CPU 上的准确率与 PyTorch 完全相同（工单 86.5%、助手 93.5%），逐题一致率 99.2% / 99.6%，概率差平均 0.007 / 0.004。FT-cf 的 0.8B Q8_0（写入温度 1.1487）一致率 99.2% / 99.8%：助手唯一不一致的一题，两边概率都在 0.5 附近（0.528 对 0.572），引擎恰好答对，所以助手准确率比 PyTorch 高 1 题（97.7% 对 97.5%）。4B FT-cf 的 Q8_0（写入温度 2.3511）同样一致：工单逐题一致率 99.4%（510 道里 507 道），不一致的 3 道两边所选答案的概率都只有 0.48–0.51，引擎多答对 1 道（96.1% 对 95.9%）；助手 477 道全部一致（99.8% 对 99.8%）；概率差平均 0.003 / 0.001。4B FT（写入温度 1.6625）已转换，端侧测试跑了 36 条后停止，不计入；4B 只完整测了推荐的 FT-cf。

**发现 2：Q8_0 比 Q4_K_M 更合适，Q4_K_M 只省内存。** 0.8B 的 Q4_K_M 文件小约 250 MiB、峰值工作集少约 500 MiB，但在这台机器的 CPU 上没有更快（单次决策中位数工单 812 毫秒、助手 909 毫秒，Q8_0 是 669 / 822 毫秒，差别没有超出发现 6 的运行波动），与 PyTorch 的逐题一致率却降到 94.9%（工单）和 97.9%（助手），个别题的概率差达到 0.46–0.58。准确率数字（87.5%）比 PyTorch 还高 1 个百分点，这是量化噪声恰好偏向正确答案，不能当作 Q4_K_M 更好的证据。4B FT-cf 也一样：Q4_K_M 文件小 1,383 MiB（2,893 MiB 对 4,276 MiB）、峰值工作集少 2,767 MiB（6,842 MiB 对 9,609 MiB），逐题一致率却从 99.4% / 100% 降到 98.2% / 99.8%，个别题的概率差达到 0.60；工单准确率 95.3%，比 PyTorch 低 0.6 个百分点（PyTorch 答对而它答错 6 道，反过来 3 道）。两种格式的时延这次没法比较（见发现 6）。所以 4B 默认用 Q8_0，内存紧时用 Q4_K_M。

**发现 3：Adreno GPU（OpenCL）比 CPU 慢，偏差也更大。** 同一个微调后 0.8B Q8_0 模型，OpenCL 版的工单单次决策中位数 1,035 毫秒（CPU 669 毫秒），一致率 97.6%（CPU 99.2%）；另外占用约 3,400 MiB 共享显存，进程提交内存 5,801 MiB。第一次用 OpenCL 版启动加载了 75 秒，第二次 15 秒（推测第一次在编译 GPU 内核，之后用了驱动缓存）。原因推测是决策模型每次只做一次约 300–500 个 token 的前向计算、不生成文字，这种短而一次性的计算在 12 核 CPU 上已经很快，GPU 的启动和数据搬运开销占了大头（推测，未做剖析）。

**发现 4：启动参数决定内存。** 默认参数（`-c 8192 -b 2048 -ub 2048`，4 个并行槽位）下，0.8B Q8_0 的提交内存 5,014 MiB、峰值工作集 2,314 MiB。改成 `-c 2048 -ub 512` 后提交内存降到 2,119 MiB，准确率不变，但单次决策变慢到约 1.2 秒（工单中位数 1,163 毫秒），推测是因为一次请求要分多轮计算（未做剖析）。只改 `-c 2048`、保留 `-ub 2048` 的对照运行跑到工单 144 条时中断，没有计入，所以还不能区分内存和时延各自来自哪个参数。

**发现 5：把规则写进提示词，在端侧更贵。** B0-policy 每个问题都带着策略全文。同一个发布版 0.8B Q8_0、同样的 CPU 参数，每条记录输入 token 的中位数工单从 488 变成 1,505、助手从 456 变成 813，单次决策中位数工单从 666 毫秒变成 4,353 毫秒、助手从 843 毫秒变成 2,435 毫秒，提交内存从 5,016 MiB 到 5,899 MiB；准确率只有 60.6% / 71.7%（与 PyTorch 的 60.8% / 71.9% 相当）。同一台笔记本上，微调后的 0.8B 用 669 / 822 毫秒就达到 86.5% / 93.5%。

**发现 6：单次运行的时延有波动。** FT 和 FT-cf 的 0.8B Q8_0 结构相同，测试时每条记录的输入 token 也逐条相同。按同一条记录配对比较，FT-cf 在工单上快 53 毫秒、在助手上慢 166 毫秒（中位数，相当于 FT 时延的约 −8% 和 +20%）。FT-cf 的第一次运行与结果汇总脚本同时进行，工单中位数是 841 毫秒，已在笔记本空闲时重测，表中是重测结果。每个配置只测了一次，没有控制机器温度和电源状态，所以 Q4_K_M 与 Q8_0 的差（工单 +21%、助手 +11%）不作结论；Adreno GPU 比 CPU 慢 49–76%、`-c 2048 -ub 512` 比默认参数慢 44–74%、B0-policy 比 B0 慢 2.9–6.5 倍，都远大于这个波动。

4B 的三次运行（发布版 Q4_K_M、FT-cf Q8_0、FT-cf Q4_K_M）每条记录的输入 token 也逐条相同。两两按同一条记录配对，时延中位数相差 7–24%；其中结构相同的发布版与 FT-cf Q4_K_M 相差 23–24%（工单 +666 毫秒、助手 +906 毫秒）。FT-cf Q8_0 测到助手集第 139 条时笔记本进入新型待机，5.4 小时后才恢复（系统日志 Kernel-Power 事件 506/507），这一条的时延因此是 5.4 小时；时延中位数含它是 4,115 毫秒、去掉是 4,113 毫秒，不受影响。Q4_K_M 在恢复后测。所以 4B 的时延只看量级（一次决策约 3–5 秒），Q4_K_M 与 Q8_0 哪个更快，这次测不出来。

**NPU 没有测。** llama.cpp 的 Hexagon NPU 后端在 Windows 上需要用 `bcdedit /set TESTSIGNING ON` 打开测试签名（可能还要关闭 Secure Boot），并把自签名证书加入受信任根证书（见 llama.cpp `docs/backend/snapdragon/windows.md`，commit 7ecb57f7）。这会降低设备安全基线，不适合在公司管理的笔记本上做，所以本次只测了不需要测试签名的 CPU 和 Adreno GPU。

| 4. 推理引擎 | 能。llama.cpp b11935 官方发布包直接运行微调后的 GGUF；0.8B Q8_0 在骁龙 X Elite CPU 上与 PyTorch 逐题一致率 99.2% 以上，单次决策时延中位数 0.65–0.98 秒；4B FT-cf Q8_0 一致率 99.4% / 100%，3.6–4.1 秒；CPU 比 Adreno GPU 快 | 第 5 节 |

### 6.2 给厂商的建议

1. **默认上 0.8B，准确率不够再上 4B。** 0.8B FT-cf 在同分布测试集上已达 86.9% / 97.5%，文件 775 MiB，单次决策时延中位数 0.65–0.98 秒。4B FT-cf 高出 9.0 和 2.3 个百分点，工单场景和"按字段套规则"都更好；代价是 4B FT-cf 的 Q8_0 在笔记本 CPU 上单次决策时延中位数 3.6–4.1 秒、峰值工作集 9,609 MiB，分别约是 0.8B 的 4–6 倍和 4 倍。工单这类规则多的场景值得评估 4B。不要用不微调的 4B 代替微调：笔记本上实测，发布版 4B Q4_K_M 的准确率 59.0% / 82.0%，比 FT-cf 0.8B Q8_0（86.9% / 97.7%）低 27.9 / 15.7 个百分点，单次决策时延中位数却是它的 3.9–4.7 倍，峰值工作集约是它的 3 倍（第 5 节的表）。
2. **发布格式默认用 Q8_0，跑在 CPU 上。** Q8_0 与训练时的结果一致性最好，0.8B 在骁龙 X Elite 的 CPU 上也不比 Q4_K_M 慢。4B 在内存紧的机器上可以用 Q4_K_M：峰值工作集少 2,767 MiB，代价是工单准确率比 PyTorch 低 0.6 个百分点，上线前要在厂商自己的测试集上复核。Adreno GPU 版更慢、偏差更大，现阶段没有理由用。
3. **按机器内存选启动参数。** 只服务本机一个用户时，不需要默认的 4 个并行槽位和 8K 上下文。本次实测 `-c 2048 -ub 512` 把 0.8B Q8_0 的提交内存从 5,014 MiB 降到 2,119 MiB，准确率不变，单次决策中位数从 669 / 822 毫秒变成 1,163 / 1,184 毫秒。只改 `-c`、保留 `-ub 2048` 的对照没有跑完，上线前要补测，弄清时延变慢来自哪个参数。
4. **训练数据要专门覆盖"只差一个字段"的情况。** 首轮 FT 的整体准确率已经很高，但只看答案因字段改变的题，0.8B 只答对一半左右（48.3% / 48.6%）。加入只改一个策略字段、标签由规则代码重算的变体后（FT-cf），0.8B 助手从 48.6% 提到 81.9%，4B 工单从 72.1% 提到 84.9%。变体每次只改一个字段，要同时看几个字段的"能否上门"仍未补上；真实项目还应加入多个字段组合变化、阈值附近取值的样本，并用同样的变体集验收（建议，本次没有验证）。
5. **先验证阈值，再决定是否分流。** 在独立校准或开发数据上选择阈值，固定后用未参与选择的数据检查覆盖率、错误率和少数类别表现。3.4 的测试集风险覆盖率只能辅助评估，不是现成的上线阈值。若需要转人工或云端模型，应由业务明确批准并单独实现；当前本机客户端没有这些兜底调用。
6. **换成真实数据时保留同一套检查。** 标签由业务规则代码或人工复核给出、按原话分组切分、留一份不同来源的分布外测试、做配对检查、与 PyTorch 逐题比对端侧结果。这些脚本都在 `scripts/` 下，可以直接复用。

### 6.3 这些结论的边界

- **数据是模拟的。** 规则、字段和客户原话都是为虚构厂商 Contoso PC 设计的；原话由大模型按事实清单生成，比真实客户的话更规整。真实数据上的绝对准确率会不同，本报告能说明的是"方法可行、量级多大、资源要多少"。
- **只训练了一次（seed 1）。** 每个结论只代表这一次运行；95% 区间反映的是测试集抽样的不确定性，不包括换一个随机种子、换一批数据带来的波动。
- **温度用同分布的校准集拟合。** 校准集与训练集来自同一个生成模型和同一套规则（`calibrate_checkpoint.py --allow-in-distribution`，脚本会对这种用法给出警告）。分布外测试的 ECE 是这一选择的检验。
- **分布外助手测试缺一类。** 13 条"应拒绝"类请求没有生成出原话，分布外助手准确率不包含这一类。
- **端侧只测了一台笔记本、一次一条请求。** 没有测并发、长时间运行发热降频、电池供电，也没有测 NPU。每个配置只测了一次，同结构模型两次运行的配对时延差可达 24%；4B FT-cf Q8_0 测试中笔记本进入过一次待机（发现 6）。4B 只完整测了推荐的 FT-cf（4B FT 跑了 36 条后停止，不计入）。
