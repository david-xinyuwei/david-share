## 摘要

**BF16 降低的尾数精度会在自回归生成过程中引入细微的舍入误差，这些误差在强化学习管道中会产生灾难性的累积效应。** 当 rollout（推理）和训练在不同引擎上执行时——例如 vLLM vs PyTorch FSDP——BF16 的舍入不一致会导致**策略分歧、梯度偏差和奖励崩溃**。

**解决方案：** 迁移到 **FP16**（10 位尾数）可实现 **24 倍更低的 KL 散度**、**1.5–2 倍更快的收敛速度**和**稳定的训练曲线**，无需任何算法修改。

## 关键发现

### 核心问题

BF16（7 位尾数）无法可靠地区分接近的动作 logits（例如 10.231 vs 10.237），导致：

- **策略漂移**：Rollout 策略与训练策略发生分歧
- **梯度偏差**：重要性采样比率变得不可靠
- **奖励崩溃**：训练在 150–600 步后变得不稳定
- **部署差距**：生产环境行为与训练时不同

### 关键指标对比

| 指标 | BF16 | FP16 | 改进 |
|------|------|------|------|
| Token 级 KL 散度 | 7.64 | 0.32 | **减少 24 倍** |
| 训练稳定性 | 150–600 步崩溃 | 稳定收敛 | — |
| 收敛速度 | 停滞或回退 | 达到近乎完美的准确率 | **快 1.5–2 倍** |
| 权宜之计成本 | FP32 推理（≈3 倍计算） | 原生 FP16（1 倍） | **消除 3 倍开销** |

## 浮点数基础

### IEEE 754 格式规范

#### FP16（半精度）

```
结构：[1 符号位 | 5 指数位 | 10 尾数位]
偏置：15
范围：±6.55×10⁴
精度：2⁻¹⁰ ≈ 0.001（≈0.1% 相对误差）
```

**特点**：
- 高分辨率（1024 个尾数分区）
- 有限的动态范围
- 适合有界数值域（RL 的 logits、Q 值）

#### BF16（脑浮点 16）

```
结构：[1 符号位 | 8 指数位 | 7 尾数位]
偏置：127
范围：±3.4×10³⁸（与 FP32 相同）
精度：2⁻⁷ ≈ 0.008（≈0.8% 相对误差）
```

**特点**：
- 宽动态范围（与 FP32 匹配）
- 粗糙分辨率（128 个尾数分区）
- 适合极端梯度分布（LLM 预训练）

## 为什么 RL 需要尾数精度

### 机制分析

1. **Logit 敏感性**：训练良好的模型中，策略 logits 差异 <0.01
2. **Softmax 放大**：小的舍入误差 → 改变动作概率
3. **Rollout 累积**：误差在 100–1000 token 序列中累积
4. **引擎不匹配**：vLLM（推理）vs PyTorch（训练）对 BF16 舍入处理不同
5. **梯度损坏**：有偏的重要性采样比率 → 错误的策略更新

### 具体示例

```python
import math

def softmax(logits):
    m = max(logits)
    exp_vals = [math.exp(x - m) for x in logits]
    return [e / sum(exp_vals) for e in exp_vals]

# 真实 logits
true_logits = [10.231, 10.237, 10.225]

# FP16 模拟（10 位尾数）
fp16_logits = [round(x * 1024) / 1024 for x in true_logits]
# → [10.2305, 10.2368, 10.2251] ✅ 排序保持

# BF16 模拟（7 位尾数）
bf16_logits = [round(x * 128) / 128 for x in true_logits]
# → [10.2344, 10.2344, 10.2344] ❌ 全部相同！

print("FP16 概率:", softmax(fp16_logits))  # 有意义的分布
print("BF16 概率:", softmax(bf16_logits))  # 均匀分布 → 随机采样
```

**结果**：BF16 将不同的动作折叠成相同的概率，迫使智能体进行随机探索。

## 训练-推理不匹配分析

### 根本原因

不同的执行引擎在实现 BF16 算术时存在微小差异：
- 融合操作内核（如 Flash Attention）
- 舍入策略（四舍五入 vs 截断）
- 中间累积的精度

在长序列（512–2048 tokens）中，这些差异导致策略输出的**指数级分歧**。

### 定量影响

| 测量指标 | BF16 | FP16 |
|----------|------|------|
| 每 token KL（rollout vs 训练） | 7.64 | 0.32 |
| 1000 tokens 累积 KL | ~7640 | ~320 |
| 策略崩溃阈值 | 150–600 步 | 未观察到 |

### 缓解策略（按有效性排序）

1. **✅ 端到端使用 FP16**（推荐）
   - 从源头消除不匹配
   - RL 领域溢出风险可忽略
   - 需要损失缩放（使用 AMP 很简单）

2. **⚠️ FP32 推理 + BF16 训练**
   - 消除不匹配但产生 3 倍计算成本
   - 训练仍暴露于 BF16 精度损失

3. **❌ 算法修复（温度、熙奖励）**
   - 无法补偿根本的精度缺陷
   - 掩盖症状而不解决根本原因

## 推理数据类型注意事项

### ⚠️ 重要背景：两种不同场景

本节讨论 **LLM 推理**场景，与前文讨论的 **RL 训练**场景不同：

| 场景 | BF16 | FP16 | 原因 |
|------|------|------|------|
| **RL 训练 + 推理** | ❌ 避免 | ✅ **推荐** | 需要尾数精度用于策略梯度 |
| **LLM 推理（BF16 训练）** | ✅ **推荐** | ❌ 可能失败 | 需要动态范围用于预训练权重 |
| **LLM 推理（FP16 训练）** | ❌ 可能失败 | ✅ **推荐** | 匹配训练 dtype |

### 关键原则：训练和推理使用相同的 Dtype

**对于预训练 LLM**（非 RL）：总是使用与训练时**相同的 dtype** 进行推理：
- BF16 训练的模型（如 Gemma 3、TPU 训练的 Llama）→ BF16 推理
- FP16 训练的模型 → FP16 推理
- 混合精度训练 → 维持相同的 autocast 策略

**对于 RL 管道**：无论预训练基础模型的 dtype 如何，都应端到端使用 FP16（见上文主要建议）。

### 案例研究：Gemma 3 推理失败

**背景**：Google 的 Gemma 3 在 TPU 上使用 BF16 优化训练。尝试用 FP16 进行推理导致灾难性失败：

| 推理 Dtype | 内存 (GB) | 输出质量 | 速度 |
|-------------|-------------|------------|------|
| **FP16** | 8.322 | ❌ **完全失败**（仅输出 EOS tokens） | 快 |
| **FP32** | 16.426 | ✅ 稳定、准确 | 慢 |
| **BF16** | 8.254 | ✅ 稳定、准确 | 快 |
| **AMP (FP16→FP32)** | 11.029 | ✅ 稳定、准确 | 中等 |

**根本原因**：BF16 训练的模型包含超出 FP16 范围（±6.5×10⁴）的权重值和激活值。直接转换导致：
- **溢出**：大数值 → `inf`
- **下溢**：小梯度 → `0`
- **NaN 传播**：无效操作损坏计算图

### 解决方案：AMP 混合精度推理

当硬件不支持 BF16 但模型需要它时：

```python
import torch

# 加载 FP16 权重以节省内存
model = load_model(dtype=torch.float16)

# 在 FP32 中运行关键操作以防止溢出
with torch.cuda.amp.autocast(dtype=torch.float32):
    output = model(input_ids)  # 计算上转换到 FP32
    logits = output.logits     # 仍然内存高效
```

**优势**：
- ✅ 数值稳定性（FP32 计算）
- ✅ 内存效率（FP16 存储）
- ✅ 无需重新训练模型
- ⚠️ 比原生 BF16 慢 30%，但比纯 FP32 快 40%

### 硬件兼容性矩阵

| GPU 架构 | 原生 BF16| 推荐 Dtype | 备用策略 |
|-------------|------------|--------------|------------|
| **A100 / H100** | ✅ 是 | BF16 或 FP16 | — |
| **V100** | ❌ 否 | FP16 + AMP | 混合精度 |
| **RTX 40xx** | ✅ 是 | BF16 (RL) / FP16 (CV) | — |
| **RTX 30xx** | ❌ 否 | FP16 + AMP | 避免 BF16 模型 |

### 部署检查清单

```python
# 1. 检查模型的原生 dtype
original_dtype = next(model.parameters()).dtype
print(f"模型训练于: {original_dtype}")

# 2. 验证硬件能力
if torch.cuda.is_bf16_supported():
    inference_dtype = torch.bfloat16
else:
    print("⚠️ 不支持 BF16，使用 AMP")
    inference_dtype = torch.float16  # + autocast 包装

# 3. 测试数值稳定性
test_output = model.generate(test_input)
assert not torch.isnan(test_output).any(), "检测到 NaN！"
assert not torch.isinf(test_output).any(), "检测到 Inf！"

# 4. 基准测试内存和延迟
memory_used = torch.cuda.max_memory_allocated() / 1e9
print(f"峰值内存: {memory_used:.2f} GB")
```

## 实现指南

### 推荐：FP16 配合 AMP

```python
import torch
from torch.cuda.amp import autocast, GradScaler

# 初始化模型和优化器
model = MyRLPolicy().half()  # 转换为 FP16
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-5)
scaler = GradScaler()  # 自动损失缩放

for batch in dataloader:
    with autocast(dtype=torch.float16):
        logits, values = model(batch.states)
        loss = compute_rl_loss(logits, values, batch.actions, batch.returns)
    
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()
    optimizer.zero_grad(set_to_none=True)
```

### 最佳实践

- **监控 KL 散度**：每批次跟踪 `rollout_policy_kl` vs `training_policy_kl`
- **梯度裁剪**：使用 `torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)`
- **避免不必要的类型转换**：保持嵌入层为 FP16；除非发生溢出，否则不要上转换到 FP32
- **损失缩放**：从缩放因子 2¹⁶ 开始，溢出时降低（AMP 自动处理）

### 调试检查清单

```python
# 1. 验证模型 dtype
assert next(model.parameters()).dtype == torch.float16

# 2. 检查推理引擎 dtype 一致性
rollout_logits = vllm_model.generate(...)
assert rollout_logits.dtype == torch.float16

# 3. 测量策略分歧
kl_div = torch.nn.functional.kl_div(
    torch.log_softmax(rollout_logits, dim=-1),
    torch.softmax(training_logits, dim=-1),
    reduction='batchmean'
)
assert kl_div < 1.0  # FP16 应 <0.5
```

## BF16 仍然适用的场景

### 为什么 SFT 可以用 BF16 而 RL 不行

根本差异在于**学习范式和梯度来源**：

#### 监督微调（SFT）— BF16 兼容

**真实标签监督**：
- 每个样本都有**确定性标签**（正确的 token）
- 损失函数：`CrossEntropy(logits, label)`
- 梯度方向**由标签决定**，而非概率差异

**对舍入的鲁棒性**：
```python
# SFT：预测下一个 token，标签 = 42
logits = [10.231, 10.237, 10.225, ...]  # Token 42 有最高 logit

# BF16 舍入：[10.234, 10.234, 10.234, ...]
# ✅ 仍然预测 token 42（top-1 准确率保持）
# ✅ 梯度方向：∇L 推高 token 42，压低其他
```

**关键特征**：
- **Top-1 鲁棒性**：只有相对排序重要，而非绝对概率
- **独立样本**：每个梯度独立计算，无累积
- **宽数值范围**：激活值跨越 10⁻⁸–10⁸（需要 BF16 的动态范围）
- **确定性收敛**：损失单调递减至零

---

#### 强化学习（RL）— 需要 FP16

**试错探索**：
- 无真实标签——智能体从**延迟、稀疏的奖励**中学习
- 策略梯度：`∇J = E[log π(a|s) · A(s,a)]`
- 梯度依赖于**概率差异**，而非标签

**灾难性舍入**：
```python
# RL：基于优势信号选择动作
π(a1|s) = 0.31  # 动作 1 概率
π(a2|s) = 0.38  # 动作 2 概率（好 0.07）
A(a1) = +0.23   # 动作 1 的优势
A(a2) = +0.31   # 动作 2 的优势

# 梯度贡献：
∇J_a1 = log(0.31) × 0.23 = -0.269
∇J_a2 = log(0.38) × 0.31 = -0.300

# BF16 将两个概率都舍入到 0.34：
∇J_a1_bf16 = log(0.34) × 0.23 = -0.248  # ❌ 错误权重
∇J_a2_bf16 = log(0.34) × 0.31 = -0.335  # ❌ 比率被破坏
```

**关键脆弱性**：
- **概率排序至关重要**：智能体必须区分 0.31 vs 0.38 以偏好更好的动作
- **指数级误差累积**：1000 步 rollout → KL 散度 7640（vs FP16 的 320）
- **紧凑数值范围**：Logits ∈ [−10, 10]（BF16 的额外范围浪费）
- **非平稳优化**：每次更新后策略改变，误差累积

---

#### 对比分析

| 维度 | SFT（BF16 ✅） | RL（需要 FP16 ⚠️） |
|------|----------------|---------------------|
| **学习信号** | 确定性标签 | 随机奖励 |
| **梯度来源** | `∂L/∂logits`（标签驱动） | `π(a) · A(a)`（概率加权） |
| **误差容忍** | ±0.008 可忽略（top-1 鲁棒） | ±0.008 破坏动作排序 |
| **累积效应** | 无（独立样本） | 指数级（序列决策） |
| **数值范围** | 10⁻⁸–10⁸（需要 BF16） | [−10, 10]（FP16 足够） |
| **收敛性** | 单调递减 | 随机，依赖探索 |

**类比**：
- **SFT**：有标准答案的选择题考试——只需选对选项（top-1）。即使分数 87 和 89 都舍入到 88，正确答案仍可识别。
- **RL**：没有答案的开放研究——必须判断"论文 A 得 87 分，论文 B 得 89 分，所以 B 更好"。如果精度将两者都舍入到 88 分，**无法区分质量**。

### BF16 可接受的使用场景

| 领域 | 理由 | 证据 |
|------|------|------|
| **LLM 预训练/SFT** | 确定性标签，宽梯度范围（10⁻⁸–10⁸） | GPT-3、Llama 证明稳定 |
| **计算机视觉** | 分类 logits 间隔良好（>1.0 差距） | ResNet、ViT 收敛不受影响 |
| **短序列 RL** | <100 tokens 最小化累积 | Atari（单帧）稳定 |
| **H100+ 硬件** | 硬件优化的 BF16 管道减少不匹配 | 需要实证验证 |

### 保留 BF16 时的迁移检查清单

1. **验证稳定性**：绘制 ≥1000 步的奖励曲线，检查崩溃
2. **测量 KL**：确保 rollout-训练 KL <2.0（vs FP16 的 <0.5）
3. **长序列测试**：用 2048-token 片段进行压力测试
4. **硬件性能分析**：确认引擎特定的 BF16 一致性

## 常见问题

### Q1：为什么不直接全用 FP32？

**A**：FP32 比 FP16 慢 2 倍且使用 2 倍内存。对于 RL，FP16 提供足够的精度（2⁻¹⁰ ≈ 0.001）同时保持吞吐量。除非调试极端数值不稳定性，否则 FP32 过于昂贵。

### Q2：FP16 会在 RL 中导致溢出吗？

**A**：很少。RL 值（logits、Q 值、优势）通常在 [−10, 10] 范围内。FP16 的范围（±6.5×10⁴）绰绰有余。使用损失缩放（AMP）防止梯度下溢。

### Q3：我的 BF16 训练没有崩溃——还需要切换吗？

**A**：可能需要。检查：
- 序列是否 <200 tokens？（短任务隐藏问题）
- 动作 logits 是否间隔良好（>0.1 差距）？（粗粒度任务容忍 BF16）
- 推理引擎是否与训练相同？（单引擎设置减少不匹配）

即使没有崩溃，FP16 也可能收敛更快并产生更高的最终性能。

### Q4：可以混合 FP16（训练）+ BF16（推理）吗？

**A**：**不可以**。这会重新引入不匹配问题。在 rollout 和训练中保持 dtype 一致。

### Q5：这适用于离线 RL 吗？

**A**：部分适用。离线 RL 避免了 rollout-训练不匹配，但仍受益于 FP16 的精度：
- Q 值估计（SAC、TD3）
- 策略梯度计算（IQL、CQL）

### Q6：如何在生产中监控不匹配？

```python
# 记录 rollout 和训练策略之间的 KL 散度
def log_policy_divergence(rollout_logits, training_logits):
    kl = F.kl_div(
        F.log_softmax(rollout_logits, dim=-1),
        F.softmax(training_logits, dim=-1),
        reduction='batchmean'
    )
    wandb.log({"policy_kl": kl})
    
    # 如果散度超过阈值则告警
    if kl > 2.0:
        logging.warning(f"高策略分歧: {kl:.2f}")
```

### Q7：对 LoRA/QLoRA 微调的影响？

**A**：**关键**。低秩适配器放大尾数误差。强烈推荐 FP16 用于：
- QLoRA（4 位量化 + LoRA）
- LLM 的 RL 微调（RLHF、RLAIF）

### Q8：这会影响基于模型的 RL（世界模型）吗？

**A**：会。世界模型预测在 rollout 视野（10–50 步）上累积误差。FP16 保持更清晰的状态分布。

### Q9：可以对某些层用 BF16，其他层用 FP16 吗？

**A**：技术上可以，但**不推荐**。复杂性超过收益。如果特定层溢出（罕见），仅将这些层上转换到 FP32。

### Q10：如何在我的硬件上验证 FP16？

```bash
# 测量 FP16 vs BF16 吞吐量
python benchmark.py --dtype float16 --batch_size 64
python benchmark.py --dtype bfloat16 --batch_size 64

# 检查数值异常
pytest tests/test_dtype_stability.py --dtype float16
```

### Q11：可以将 BF16 训练的模型转换为 FP16 进行推理吗？

**A**：**极其危险**。如 Gemma 3 所示，BF16 模型可能包含超出 FP16 范围（±6.5×10⁴）的数值。安全选项：
1. **最佳**：如果硬件支持，使用 BF16 推理（A100、H100、RTX 40xx）
2. **可接受**：使用 AMP 混合精度（FP16 存储 + FP32 计算）
3. **最后手段**：纯 FP32 推理（2× 内存成本）

**绝不**要在未测试的情况下直接将 BF16 权重作为 FP16 加载——模型可能只输出垃圾或 EOS tokens。

### Q12：为什么我的模型在训练时有效，但使用相同 dtype 推理时失败？

**A**：检查**引擎差异**：
- 训练：PyTorch FSDP 使用 `torch.nn.functional` 操作
- 推理：vLLM/TensorRT 使用优化的融合内核

即使 dtype 相同，不同引擎处理舍入/累积的方式也不同。解决方案：
- 使用与训练相同的推理引擎（例如都用 vLLM）
- 监控引擎间的 KL 散度
- 如果散度 >2.0，切换到 FP32 或使用推理引擎重新训练

## 常见误区

### ❌ "BF16 = FP32 范围 → 总是更安全"

**现实**：RL 不需要 FP32 的范围。策略 logits 在 [−10, 10] 范围内。BF16 为未使用的余量牺牲精度。

### ❌ "精度差异可以忽略"

**现实**：在单步推理中，是的。但在 1000 步 RL rollout 中，舍入误差指数级复合。

### ❌ "损失缩放修复 BF16 问题"

**现实**：损失缩放防止下溢，而非精度损失。无论如何缩放，BF16 的 7 位尾数都无法表示 10.231 ≠ 10.237。

### ❌ "切换优化器可以补偿 dtype 选择"

**现实**：Adam vs SGD 影响收敛速度，而非数值精度。优化器选择无法恢复丢失的尾数位。

### ❌ "BF16 训练比 FP16 快"

**现实**：在现代 GPU（A100、H100）上，FP16 和 BF16 有相同的吞吐量。FP16 避免不匹配引起的不稳定性，**减少到收敛的总时钟时间**。

### ❌ "多次 dtype 转换无害"

**现实**：每次 FP32 → BF16 → FP16 转换都会引入舍入。TRL + QLoRA 管道在训练开始前就经历 3–4 次往返转换。

### ❌ "FP16 总是溢出"

**现实**：使用损失缩放（AMP 中的标准），FP16 溢出在 RL 中很少见。监控梯度中的 `inf`/`NaN`；如果持续，检查模型架构，而非 dtype。

### ❌ "H100 使 dtype 选择无关紧要"

**现实**：H100 加速 BF16 操作但不消除精度限制。FP16 在所有硬件上对 RL 仍然更优。

### ❌ "任何 16 位 dtype 只要模型能装入内存就能用于推理"

**现实**：如 Gemma 3 所示，将 BF16 权重作为 FP16 加载会导致完全的推理失败（仅输出 EOS tokens）。**训练和推理之间的 dtype 不匹配是灾难性的**，而不仅仅是性能问题。

### ❌ "AMP 只用于训练，不用于推理"

**现实**：AMP 混合精度是一种有效的推理策略，当：
- 硬件缺乏原生 BF16（例如 V100、RTX 30xx）
- 模型在 BF16 中训练但部署 GPU 不支持它
- 您需要平衡内存（FP16 存储）和稳定性（FP32 计算）
