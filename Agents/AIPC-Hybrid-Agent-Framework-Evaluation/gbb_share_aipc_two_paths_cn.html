Hi Team,

分享一下最近帮联想 Qira 团队做的 AIPC 本地 agent 执行评估。核心问题：如果端侧 AI assistant 要在 Windows 上安全执行本地 action，架构怎么选？

两条实现路径（来自 Build 2026 BRK262 / KEY01）：

Path A：MAF 贯穿Path B：MXC + ProcessContainer
适用完整 agent workflow：规划、工具、HITL、CodeAct、恢复只需受控本地执行，不用完整 agent loop
执行方式MAF 承载推理循环；Hyperlight sandbox 跑生成代码MXC policy 选 ProcessContainer（默认）或 Hyperlight
已验证MAF + Hyperlight CodeAct + 4 个 host tools 在 Windows VM 上跑通MXC 0.7 network/filesystem/UI policy + task-scoped capability catalog

跑在 Azure 上：评估使用 Azure OpenAI（gpt-5.4 via APIM）做云端 reasoning + 一台 Standard Windows VM 模拟客户 AIPC。生产环境里 AIPC 是客户自己的设备，Azure 消耗主要是 AOAI token（云端模型调用）+ APIM 网关。如果客户大规模部署 Hyperlight/CodeAct，还可以走 Foundry Hosted Agent 云端托管。

关键结果：

能力Path A (MAF)Path B (MXC)
Network block/allowN/A（框架层）✅ curl exit=6 blocked, exit=0 allowed
Filesystem scopingN/A✅ readwritePaths 在 stock Win11 上可用
Task-scoped UI policyN/A✅ text=blocked, drawing=allowed（同一 exe）
Sandbox code execution✅ Hyperlight micro-VM, 首轮 36msProcessContainer 跑轻量任务
Cross-turn state✅ 4 turns 变量跨轮保留Proto 分支（暂未进 mainline）
Host tool callbacks✅ read_csv, screenshot, system_info, list_filesN/A（MXC 不管 tool callback）

对 Azure 生意的意义：联想在评估 Qira（AIPC OS agent）的 Windows 本地执行架构。走 MAF + Hyperlight = AOAI 消耗 + Foundry hosting。走 MXC 做本地 policy governance = Windows 平台 play，但 reasoning 层仍然需要 AOAI。两条路径都意味着 Azure AI token 消耗作为云端主干。
