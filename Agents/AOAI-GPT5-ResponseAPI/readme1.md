# Using the Azure OpenAI GPT‑5 / Codex Responses API: Reasoning Chain Reuse, Encryption, Summaries, and Cost Analysis

## TL;DR (Quick Findings)

- **`reasoning.effort` is the decisive variable controlling the length of reasoning tokens** (see [Table 2: AB Comparison](#table-2-ab-test-data-r1-vs-r2-r2-with-previous_response_id))
  - `minimal` effort produces almost no reasoning chain (ratio≈0%); `low` effort ~0%–50%; `medium` / `high` can reach 70%–93%.
  - Setting `"summary":"detailed"` does NOT increase reasoning token count. Length is governed by `effort`.

- **`previous_response_id` enables direct cross-turn reasoning chain reuse** (see [Mechanism Deep Dive](#core-mechanism-deep-dive))
  
  Reasoning token reuse conditions (three key scenarios):
  1. **assistant → user**: If the previous turn ended with an assistant message, the Responses API will zero out all earlier reasoning tokens preceding that assistant message in the next call. Cached tokens become 0.
  2. **Consecutive function calls**: If multiple function call turns occur in succession, reasoning tokens are preserved; cached tokens can grow as prefix reuse accumulates.
  3. **Modality switch**: If between function call outputs modalities change (e.g., prior output pure text, next turn includes an image: `function_call_output:string + role:user type:input_image`), reasoning tokens still reuse, but cached tokens may drop to 0 (multi-modal routing shift).

- **Encrypted mode encrypts the reasoning chain, not the final visible output** (see [Table 1: Encrypted Scenarios](#table-1-multi-scenario-token-data-including-cache-hits) and [Two Encryption Modes](#4-two-modes-of-encrypted-reasoning-chains))
  - `include=["reasoning.encrypted_content"]` returns an encrypted reasoning blob you can store and replay.
  - `store=False`: server does not retain plaintext (ZDR/GDPR compliant) but cannot account for reasoning usage server-side.
  - `store=True`: server holds plaintext (full usage metrics) and can also return encrypted blob for local persistence.

- **Responses API advantages vs classic Chat Completions API** (see [Responses API vs Chat Completions](#responses-api-vs-chat-completions-api))
  - Native reasoning chain management & reuse (including encrypted chains)
  - Reasoning chain summarization (`concise` / `auto` / `detailed`)
  - Multi-turn reuse + conditional reasoning invocation
  - Integrated function calling, multimodal IO, structured merging

- **Experimental conclusions** (see [Full Experimental Data](#experimental-design--results-analysis))
  - In `identical_dialogue`, high effort can save up to **94.3%** reasoning tokens.
  - In `identical_code`, savings range **36%–66%** (realistic code iteration scenario).
  - Prompt cache hit requires: prefix ≥1024 tokens + identical params + stable `previous_response_id` reuse.
  - Detailed checklist & best practices: see [Operational Playbook](#checklists--operations-playbook).

## Background & Problems

In productionizing LLM workflows, the following engineering pain points recur:
1. **Lost multi-turn reasoning chains** – Each turn re-derives logic from scratch, wasting compute and harming consistency.
2. **High context maintenance overhead** – Chat Completions requires full message history each turn (costly; context window pressure).
3. **No direct access or reuse of previous reasoning** – Cannot fetch prior chain-of-thought (especially encrypted forms) to feed forward.
4. **Compliance & data sovereignty** – Under ZDR/GDPR constraints, providers shouldn’t retain plaintext reasoning, while customers still want local reuse.
5. **Reasoning observability & cost governance** – Need to inspect reasoning token proportion without exposing raw chain-of-thought; must validate the real cost impact of settings like `"summary":"detailed"`.

## Core Mechanism Deep Dive

### 1. Reasoning Tokens vs Cached Tokens

Two orthogonal optimization dimensions:

- **Reasoning Tokens**
  - Internal chain-of-thought tokens generated by the model
  - Reside in hidden `type=reasoning` segments aligned with assistant output
  - Controlled primarily by `reasoning.effort` (minimal/low/medium/high)
  - Billed as output tokens; not directly surfaced to end-user
  - Reused via `previous_response_id` or by replaying `reasoning.encrypted_content`

- **Cached Tokens**
  - Prompt Cache hits: previously processed input prefix tokens
  - Reported in `input_tokens_details.cached_tokens`
  - Dependent on stable prefix (≥1024 tokens), identical parameters, routing stability
  - Priced at discounted cached-input rate (often ~10% of normal input cost)

**Relationship:**
- Reasoning reuse = logical continuity (avoid rethinking)
- Cache hits = cost / latency reduction on prompt ingest
- Best practice aims for both simultaneously.

### 2. `previous_response_id` Reuse Mechanics

#### 2.1 Principle
Link turn N to turn N+1 so the server can load and extend the prior reasoning chain:
```python
# Round 1
resp1 = client.responses.create(
    model="gpt-5",
    input=[{"role": "user", "content": "Who was stronger historically, Cao Cao or Sun Quan?"}],
    reasoning={"effort": "high", "summary": "detailed"},
    store=True
)

# Round 2
resp2 = client.responses.create(
    model="gpt-5",
    input=[{"role": "user", "content": "Please restate your conclusion"}],
    previous_response_id=resp1.id,
    reasoning={"effort": "high", "summary": "detailed"}
)
```

#### 2.2 Three Canonical Behaviors
| Scenario Type              | Reasoning Token Behavior                 | Cached Token Behavior       | Typical Use Case                        |
| -------------------------- | ---------------------------------------- | --------------------------- | --------------------------------------- |
| assistant → user           | Prior reasoning cleared                  | 0 (no cache reuse)          | New user query after free-form answer   |
| Consecutive function calls | Reasoning retained across calls          | Increases (prefix stable)   | Tool chain (call → parse → present)     |
| Modality switch            | Reasoning retained                       | May reset (routing change)  | Text function output → image augmented  |

**Observed Evidence:**
- FUNCTION_R2: reasoning=0 (simple restatement), cached=3840 (stable prefix)
- BASIC_R2: reasoning=192 (partial reuse), cached=3456
- ENCRYPTED_R2 (store=False): reasoning=384 reused; cached=3456

### 3. Prompt Cache Hit Mechanics

#### 3.1 Construction Order
```
System Prompt → Tool Definitions → Messages
```
Within Messages: User → Assistant (hidden reasoning) → Function Call → Function Call Output

#### 3.2 Reasoning Placement
Hidden inside assistant message (`type=reasoning`), not a standalone message.

#### 3.3 Cache Hit Requirements
- Leading prefix block ≥1024 tokens
- Identical from start of prompt (system + tools + earliest messages)
- If System alone ≥1024 tokens: stable block excludes reasoning (pure system)
- If System <1024 tokens: block spills into tools/messages (may include reasoning but fragile)

#### 3.4 Why Include Messages / Reasoning in Cache?
- If included, those tokens are billed at cached rates and recompute is avoided
- Missed caching means logical reuse still happens but compute cost not reduced

#### 3.5 Logical vs Cost Reuse
- Logical: `previous_response_id` / encrypted replay
- Cost: prompt cache hits on shared prefix

#### 3.6 Server Patterns
- assistant → user: RT cleared, CT=0
- assistant → function_call: RT preserved, CT stable/growth
- consecutive function_call: RT preserved, CT grows
- modality shift: RT preserved, CT may zero

### 4. Two Modes of Encrypted Reasoning Chains

#### 4.1 `store=True`: Stateful Reuse (Server Holds Plaintext)
```python
resp1 = client.responses.create(
    model="gpt-5",
    input="Question",
    store=True,
    include=["reasoning.encrypted_content"]
)
resp2 = client.responses.create(
    model="gpt-5",
    input="Follow-up",
    previous_response_id=resp1.id,
    store=True,
    reasoning={"effort":"high"}
)
```
**Characteristics:**
- Server can account for reasoning usage precisely
- Can return encrypted blob simultaneously
- Good for observability + reuse

#### 4.2 `store=False`: Stateless Replay (Compliance Mode)
```python
resp1 = client.responses.create(
    model="gpt-5",
    input="Question",
    store=False,
    include=["reasoning.encrypted_content"]
)
# Client persists encrypted blob locally
context = [{"role": "user", "content": "Follow-up"}] + resp1.output
resp2 = client.responses.create(
    model="gpt-5",
    input=context,
    store=False,
    include=["reasoning.encrypted_content"]
)
```
**Characteristics:**
- Provider never stores plaintext (ZDR/GDPR alignment)
- Server may not expose accurate reasoning usage (often 0)
- Encrypted blob is the carrier for logical reuse
- Still can trigger prompt cache hits (empirically cached_tokens=3456)

## Responses API vs Chat Completions API

| Feature            | Chat Completions                | Responses API                                                   |
| ------------------ | -------------------------------- | ---------------------------------------------------------------- |
| Context mgmt       | Must resend full messages        | `previous_response_id` server-side chain retention               |
| Reasoning reuse    | None                             | Plain ID or encrypted blob reuse                                 |
| Reasoning summary  | Not built-in                     | `reasoning.summary` safe abstraction (no raw CoT exposure)       |
| Encrypted reasoning| Not available                    | `store=False` + encrypted replay (privacy + reuse)               |
| Tool output struct | Intermingled in messages         | Typed outputs: message / tool_call / reasoning                   |
| Multimodal struct  | Limited                          | Native typed multimodal IO & merging                             |

**Capability Uplift:** structured reuse, encrypted compliance, safe summarization, richer tool & multimodal orchestration.

## Experimental Design & Results Analysis

Six scenario families validate reasoning reuse, encryption behavior, and prompt cache interactions.

### Design Principles
- Two rounds: R1 builds reasoning; R2 reuses via `previous_response_id`
- Long system prompt (≥1024 tokens) to study cache hits
- Consistent params: `effort=high`, `summary=detailed` unless AB testing
- AB: vary effort × summary × task archetype

## Integrated Analysis Conclusions
1. `previous_response_id` + stable prefix = consistent prompt cache hits in R2.
2. `effort` drives reasoning volume; higher effort magnifies reuse payoff.
3. Task archetype shapes savings (dialogue restatement > code refinement).
4. Encrypted stateless replay still achieves both logic reuse and cache savings.
5. Always pair logical reuse metrics (reasoning_tokens drop) with cached_tokens to see dual-layer optimization.

## Checklists & Operations Playbook

### A. Reasoning Reuse (Logical Continuity) Checklist
- Client signals (any of):
  - R2 carries `previous_response_id` (store=True / default)
  - R2 replays encrypted reasoning blob (store=False path)
- Indicators:
  - R2 reasoning_tokens << R1 (except explanatory expansions)
  - Consecutive function_call outputs yield near-zero new reasoning
- Strong evidence: removing `previous_response_id` increases reasoning_tokens & stylistic drift.

### B. Prompt Cache Hit Checklist
- `usage.input_tokens_details.cached_tokens > 0`
- Prefix ≥1024 tokens (long system prompt first)
- Ordered: System → Tools → Messages identical
- Parameter parity: `store`, `tools`, `reasoning.effort`, `summary`, `parallel_tool_calls`
- Stable routing (avoid abrupt modality switch)

### C. Combined Matrix (store × encryption × prev_id × reuse × cache)
| Mode | store | encrypted_content included | Use prev_id? | Reuse Carrier | Logical Reuse | Cache Potential | Example | Notes |
|------|-------|----------------------------|--------------|---------------|---------------|-----------------|---------|-------|
| A    | True  | Optional                   | Yes          | Server-held plaintext | Yes | High | BASIC_R2 | Simplest |
| B    | True  | Yes                        | Yes          | Plaintext + encrypted copy | Yes | Varies (some routes hide metric) | ENCRYPTED_R2 store=True | Dual retention |
| C    | False | Yes                        | No           | Encrypted replay in input | Yes | High (if prefix stable) | ENCRYPTED_R2 store=False | Stateless compliance |
| D    | False | No                         | No           | None            | No            | Prefix-only (no reasoning reuse) | — | Not recommended |

### D. Fast Triage Flow
1. Was `previous_response_id` or encrypted replay used?
2. Did R2 reasoning_tokens drop? (If not explanatory expansion.)
3. Are cached_tokens > 0? If not, check prefix length & param drift.
4. A/B without `previous_response_id` to confirm reuse effect.

### E. Best Practices
- Always anchor with ≥1024 token stable system prompt.
- Keep tool schemas static between turns.
- Reuse with `previous_response_id` when possible; fallback to encrypted replay for `store=False`.
- For multi-step tool flows, chain via function_call → function_call_output to avoid reasoning resets.

## Production Implementation Examples

### Stable Prompt Cache + Reasoning Reuse
```python
SYSTEM_PROMPT = "Long stable instructions ..." * 300  # >=1024 tokens
TOOLS = [...]

# Round 1
r1 = client.responses.create(
    model="gpt-5",
    input=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": "Initial task"}
    ],
    tools=TOOLS,
    store=True,
    reasoning={"effort":"high","summary":"detailed"},
    parallel_tool_calls=False
)

# Round 2
r2 = client.responses.create(
    model="gpt-5",
    input=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": "Follow-up"}
    ],
    previous_response_id=r1.id,
    tools=TOOLS,
    store=True,
    reasoning={"effort":"high","summary":"detailed"},
    parallel_tool_calls=False
)
```

### Compliance (Stateless Encrypted Reuse)
```python
r1 = client.responses.create(
    model="gpt-5",

    store=False,
    include=["reasoning.encrypted_content"],
    reasoning={"effort":"high","summary":"detailed"}

# Persist r1.output locally (contains encrypted reasoning segment)

  {"role":"system","content":SYSTEM_PROMPT},
```

- Codex delivers higher throughput (tokens/sec) and lower sec/1k in refactor & large tasks.

## Troubleshooting Quick Reference
| Symptom | Likely Cause | Resolution |
|---------|--------------|-----------|
| R2 reasoning not reduced | Missing `previous_response_id` or task changed | Ensure prev_id or encrypted replay; keep follow-up semantically aligned |
| `cached_tokens` always 0 | Prefix <1024 or param drift | Lengthen stable system prompt; unify tool & reasoning settings |
| store=False reasoning shows 0 | Expected (server can’t count plaintext) | Use output quality & cache hits as proxy |
| prev_id not found error | Using store=False or expired ID | Use encrypted replay path or set store=True |
| Cache disappears after modality shift | Routing change | Logic reuse still valid; adapt prefix strategy |

## Summary & Best Practices

1. **Effort scales reasoning token budget**; tune for trade-off between observability and cost.
2. **Leverage `previous_response_id`** for the most stable logical & cost synergy; fallback to encrypted replay under compliance.
3. **Engineer a ≥1024 token stable prefix** (System → Tools) for repeatable cache hits.
4. **Measure both reasoning_tokens and cached_tokens** to capture logical + compute efficiency.
5. **Use high effort only where reuse probability is high** (e.g., iterative refinement, structured multi-turn tasks).
